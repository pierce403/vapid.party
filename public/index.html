Existing XMTP integrations

One small signal across a focused path.

The restricted Converge and operator XMTP integrations keep matching, app routing, and browser delivery inside a Cloudflare Worker, D1, Queue, and singleton Container. Public apps can register XMTP routes only after an installation-key proof, then choose Web Push or a signed HTTPS callback.

01 / Listen

Follow the live XMTP stream

A singleton Container receives production XMTP v3 events as they arrive.

02 / Match

Resolve an app-scoped route

Topic HMAC epochs and sender suppression decide whether an alert should move.

03 / Deliver

Queue a minimal availability hint

Web Push or a signed callback receives opaque activity, then the XMTP client performs authoritative sync.

Experimental

XMTP SubscribeAll has no durable replay cursor. A listener restart or disconnect can miss a push hint; the receiving XMTP inbox remains the source of truth. Public enrollment proves possession of the claimed installation key, but normal XMTP client sync remains authoritative after every hint.

Missing an alert?

Trace the path in order.

  1. Confirm global ingestion. The live rail should show both the XMTP listener ready and route bridge synced.
  2. Confirm actual XMTP matching. In the client app, compare registered topics and HMAC epochs, then check its last XMTP match. Global health cannot prove one app route matched.
  3. Confirm target delivery separately. A diagnostic canary proves a provider path only; it does not prove that a real XMTP message matched the registration.

Privacy boundary

Signals, not messages.

The listener matches encrypted event metadata inside the Container. The delivery pipeline carries only the minimum opaque activity hint needed to wake the right app.

  • No message text, preview, or sender name
  • No conversation ID or attachment URL
  • No XMTP ciphertext in Queue or Web Push payloads
  • App and installation routes stay isolated
